# development-workflow Specification

## Purpose
为 OfferFlow 提供可从仓库恢复的阶段开发约定，使需求、角色职责、设计、任务、审查、验证和归档形成可回查记录。流程保留用户已经给出的授权，同时区分尚未确认的业务设计，支持在当前工具环境中逐步交付个人项目。

## Requirements

### Requirement: 仓库入口与角色定位

仓库 SHALL 提供可定位项目上下文、工作流、制品模板和角色职责的入口，并明确角色文件不是自动运行配置。

#### Scenario: 助手从仓库开始新阶段

- **WHEN** 助手读取仓库 AGENTS.md 和工作流入口
- **THEN** 能找到本阶段相关规范与角色契约，并知道默认按顺序执行而非自动启动子 agent

### Requirement: 制品依赖与可验证行为

每个正常阶段 change MUST 明确需求、行为、设计和任务，tasks 依赖 specs 与 design，行为场景采用 WHEN / THEN。

#### Scenario: 为新模块准备方案

- **WHEN** 新模块的 proposal 已完成且行为与设计制品已准备
- **THEN** 可以生成引用验收条件或场景的任务清单，尚未完成的任务保持未勾选

### Requirement: 首次业务实现确认

工作流 MUST 区分用户需求、设计建议和确认记录；没有整体业务设计确认时不得开始业务代码实现。

#### Scenario: 用户只要求初始化工作流文档

- **WHEN** 用户明确要求沉淀工作流文件但尚未确认整体业务设计
- **THEN** 完成文档阶段，业务设计保持待确认，不能据此初始化业务工程

### Requirement: 已有授权的连续执行

助手 SHALL 在已授权阶段内连续完成实现、测试、修复、审查和交付，不重复要求相同确认，也不扩展到未授权范围。

#### Scenario: 用户批准当前模块并授权阶段推送

- **WHEN** 当前模块的设计和实施范围已经得到明确批准
- **THEN** 在该范围内完成适用检查和交付，只对实质新增范围或关键缺失信息请求输入

### Requirement: 状态与证据恢复

change MUST 保存实际状态、授权范围、阻断项和转换证据；续跑时读取记录，不用文件存在代替验收通过。

#### Scenario: 必要验证尚未运行

- **WHEN** 所需验证工具不可用或关键业务输入缺失
- **THEN** 保留当前阶段及 NOT_RUN 或待输入原因，只继续独立工作，不标记验收完成

### Requirement: 审查的证据和职责

审查 MUST 根据真实文件或 diff 记录问题、影响和责任归属，单助手审查标为 SELF_REVIEW。

#### Scenario: 同一助手完成文档实施与审查

- **WHEN** 没有被授权的独立审查 agent 参与当前 change
- **THEN** 审查报告如实标注 SELF_REVIEW，不能声明独立审查已经发生

### Requirement: 与变更相称的验证

验证 SHALL 对应变更的真实风险；纯文档检查格式、引用和语义，业务阶段执行必要测试与工程检查。

#### Scenario: 当前只有文档和配置

- **WHEN** change 没有 Java 工程或业务代码变更
- **THEN** 记录实际文档检查，不声称 Java 编译或业务测试通过，也不为此强制初始化工程

### Requirement: 验证后的规范同步与归档

归档 MUST 在验收和必要审查通过后同步已完成的 delta，保留无关规范并保存 change 过程记录。

#### Scenario: 文档初始化已经验收

- **WHEN** 工作流制品及引用通过检查且没有未解决阻断问题
- **THEN** 将工作流规范同步到稳定 specs，并按项目时区日期归档本次 change，不同步计划中的业务功能

### Requirement: 阶段交付和公开数据隔离

阶段交付 MUST 只提交当前 change 的公开文件，采用普通 Git 推送，并报告实际结果；原始参考资料、凭据和个人求职数据不得提交。

#### Scenario: 准备公开推送工作流阶段

- **WHEN** 已授权阶段完成验证、审查及归档
- **THEN** 核对候选文件和远程后提交、推送，成功或失败均按实际结果报告，不夹带原始附件或本地配置
