## MODIFIED Requirements

### Requirement: 首次业务实现确认

工作流 MUST 区分用户需求、设计建议和确认记录；业务代码只实现当前用户已确认或明确授权的范围。用户明确要求开始工程基础 change 时可以完成该工程阶段，不将其视为所有业务设计建议已批准。

#### Scenario: 用户只要求初始化工作流文档

- **WHEN** 用户明确要求沉淀工作流文件但尚未确认整体业务设计
- **THEN** 完成文档阶段，业务设计保持待确认，不能据此初始化业务工程

#### Scenario: 用户明确要求开始首个开发阶段

- **WHEN** 用户要求按工作流完成首个开发 change 且工程基础阶段范围清楚
- **THEN** 可以初始化和验证该工程基础，后续业务决定仍在对应 change 复核

### Requirement: 阶段交付和公开数据隔离

阶段交付 MUST 只提交当前 change 的公开文件，采用普通 Git 推送，并报告实际结果；原始参考资料、凭据和个人求职数据不得提交。一个 change 在实现、审查、验收和归档完成后统一推送 GitHub 一次，不在中间阶段推送。

#### Scenario: 准备公开推送工作流阶段

- **WHEN** 已授权阶段完成验证、审查及归档
- **THEN** 核对候选文件和远程后提交、推送，成功或失败均按实际结果报告，不夹带原始附件或本地配置

#### Scenario: 当前 change 正在实施或修复

- **WHEN** 同一 change 的方案、代码或验证仍在进行
- **THEN** 相关修改留在本地，完成完整交付后统一推送一次
